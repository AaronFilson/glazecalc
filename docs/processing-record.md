## Processing activities

and people who write to a Glazecalc address. No special categories of data are processed on purpose; free-text fields
(notes, titles) hold whatever a potter types.

## Recipients and transfers

- **Amazon Web Services, Inc.**, processor, in the United States, Oregon (us-west-2): EC2 and EBS (the server),
  S3 (dumps, inbound mail), SES (mail out and in), SNS (bounce notices), Lambda and CloudWatch Logs (the mail
  forwarder; its log holds message ids only).
- **Terms:** the AWS Data Processing Addendum, incorporated by the
  [AWS Service Terms](https://aws.amazon.com/service-terms/) §1.14 (Service Terms **last updated 1 October 2026**,
  checked 13 October 2026): §1.14.1 the DPA, §1.14.2 the Supplementary Addendum, §1.14.3 the 2021 Standard
  Contractual Clauses (controller-to-processor and processor-to-processor), §1.14.4 the UK GDPR Addendum and the Swiss
  Addendum. Nothing to sign; they apply to any AWS account processing Customer Data. Save a PDF of the Service Terms
  outside the repo at each review.
- **Transfer safeguard:** Amazon.com, Inc.'s certification under the EU–US Data Privacy Framework, with the UK
  Extension and the Swiss–US DPF (adequacy decision
  [(EU) 2023/1795](https://eur-lex.europa.eu/eli/dec_impl/2023/1795/oj)); check and date the entry at
  [dataprivacyframework.gov](https://www.dataprivacyframework.gov/list) at each review. Fallback: the SCCs above. The
  DPF is in force but challenged (appeal C-703/25 P; the EDPB's letter of 31 July 2026). People who sign up directly
  with Glazecalc are not themselves a Chapter V transfer (EDPB Guidelines 05/2021, Example 1); the hand-over to AWS is.
- **Google (Gmail)** holds mail forwarded to the owner, and replies sent from it.
- **Google, GitHub and Microsoft, for sign-in**, each a separate controller, only for people who choose "Continue
  with Google", "Continue with GitHub" or "Sign in with Microsoft": the browser goes to the provider, which sends back
  its id for the person and their email (Google and Microsoft: the `openid email` scopes; GitHub: `user:email`).
  Microsoft also sends the id of the person's directory (`tid`: their organization's, or Microsoft's own for personal
  accounts), kept with its `sub` as the link ([ADR 23](adr/0023-microsoft-sign-in.md)); its email is never trusted, so
  a new account made with it confirms the address by the usual emailed link. Glazecalc sends them nothing about the
  person beyond the sign-in request itself, and the server calls them only to finish a sign-in, and Microsoft's key
  set to check its tokens (`server/lib/oauth.ts`). No provider script loads on Glazecalc's pages.
- **AI apps a person connects** (Claude, ChatGPT and others), each a separate controller, only when the person
  says yes on the consent page or gives one an access token: the app receives what its tools return from the
  person's records, at the person's request, and is responsible under its own policy for what it does with it. No
  new processor: Glazecalc's own authorization server runs on the same EC2 instance
  ([ADR 0024](adr/0024-authorization-server.md)), and when an app names itself by an https address (CIMD) the
  server fetches that document from the app's own host with a plain `GET` that carries nothing about the person
  (`server/oauth/cimd.ts`).
- Not recipients: GitHub otherwise (only what a person posts in an issue themselves), Let's Encrypt (no user data), the uptime
  check (sees `/api/health` only).

## Security measures (Art. 32)

- Passwords hashed with bcrypt (cost 10); reset and confirmation tokens stored only as SHA-256 hashes, single use,
  30-minute links.
- Optional two-step sign-in (passkeys, authenticator apps, recovery codes; [ADR 0014](adr/0014-two-step-sign-in.md)).
  Authenticator-app secrets are encrypted with `MFA_KEY` (AES-256-GCM, the user id as associated data) and recovery
  codes hashed with it (HMAC-SHA256), so the dumps in S3 hold no working secret or code. `MFA_KEY` is a SecureString in
  SSM (`/glazecalc/mfa-key`), never in a dump or the repository, with an offline copy kept by the owner; each copy of
  the site (staging) has its own. No HTTP route can turn another account's two-step sign-in off.
- HTTPS everywhere with HSTS; the session cookie is HttpOnly, Secure, SameSite=Strict, path `/api`; the same-origin
  check on every change.
- Rate limits on sign-in, sign-up, password reset and trials; equal-time sign-in failures.
- Content-Security-Policy limiting loads to the site itself (`default-src 'self'` from nginx; inline scripts only by
  hash, inline styles only by nonce); `Cache-Control: no-store` on API replies.
- Access tokens stored only as SHA-256 hashes with a 4-character hint, compared in constant time, never logged or put
  in a URL; each expires; they reach only the record routes their scopes allow (default deny), never the account,
  password, sign-in or export routes; tokens that do not work are rate-limited per address (a token that works is never
  held up by that limit); an account's token requests are limited to 120 a minute and 5,000 a day (its MCP requests
  to 300 and 20,000), changes made with tokens to 60 a minute and 5,000 a day, and each token may move at most 100 records an hour to the Trash. A token cannot push entries out of a full
  Trash, nor the version from before its changes out of a record's history; an undo keeps what it replaced.
- Connected AI apps ([ADR 0024](adr/0024-authorization-server.md)): the code flow with PKCE (S256) only, public
  clients, refresh tokens that rotate (a second use ends the connection), tokens for the MCP endpoint alone (opaque,
  1 hour) and refused under `/api`; codes and tokens stored only under a SHA-256 of their value; every request
  checks the connection's row, so revoking it stops the app at once; changing records only when the person ticks it,
  reached by step-up; the consent page takes the web session only, refuses trials and unconfirmed addresses, and
  cannot be framed. CIMD fetches reach only the public internet (https on 443, a host name, the resolved addresses
  checked and connected to directly, no redirects, 5 seconds, 5 kB, JSON only), never this machine, its network or
  the cloud's metadata service.
- Share links: the secret is 256 random bits after `#` in the address, so it never reaches nginx's or the app's logs or
  a Referer; the page sends it in a header and only its SHA-256 is stored. Shared pages carry `X-Robots-Tag: noindex`,
  `Referrer-Policy: no-referrer` (and both as `<meta>`), are not in the sitemap or prerendered, and are rate-limited
  per address. What a link shows is an allowlist of fields; a new field on a recipe stays private until it is added.
- MongoDB with its own user and password, reachable only on the Docker network; no published port.
- Encrypted EBS volume and snapshots, S3 default encryption, public access blocked; the setup never turns on versioning for the backup bucket (check the live bucket, plan item 7).
- Least-privilege IAM: the deploy role runs only `deploy.sh`; the mail user may only send from its addresses; no stored
  keys in GitHub (OIDC).
- Logs kept short and without email addresses; the deletion log re-applied on every start and restore.
- Admin access is the owner's Session Manager shell; nothing records what an admin does (plan item 24).

## Lawful basis note

- **Contract (Art. 6(1)(b))** covers the account, two-step sign-in, the saved work (with its Trash and earlier
  versions), access tokens, connected AI apps and their activity log, share links, the session cookie, the emails about the account and the trial. Each is what the person asked for; without an email address there is no account (sign-in and password
  reset need it). When the account is deleted, the contract ends and the data goes, at once from the live database
  and within 30 days from backups. Nothing is kept on another basis afterwards, except the id-only deletion log.
- **Legitimate interests (Art. 6(1)(f))** cover the logs, rate limits, backups, the deletion log, the SES suppression
  list and answering mail. Balancing:
  - _Interest:_ keeping the service secure and available, stopping abuse (password guessing, sign-up floods), not
    losing people's work, proving and re-applying deletions, and keeping the right to send mail (SES suspends senders
    whose bounces and complaints run high). Recital 49 names network and information security as a legitimate
    interest.
  - _Necessity:_ each holds the least that does the job: no email in any log, ids only in the deletion log, rate-limit
    counts only in memory, and short fixed periods (14 days, 30, 37).
  - _The person's side:_ the data is ordinary (IP addresses, an email address on a do-not-mail list), it is expected
    for any website, it is never used for anything else, nobody but AWS sees it, and the notice states each item and
    period. A person can object by writing to `privacy@glazecalcapp.com`; security logs are usually kept anyway on
    compelling grounds (Art. 21(1)), and the answer is recorded.
  - _Outcome:_ the interests are not overridden.
- **Consent** is used for nothing. Every cookie and storage key is strictly necessary for a service the user asked for
  (ePrivacy Art. 5(3)), so there is no banner. Analytics, embeds or remote fonts would change that.
- **Children:** the site is not directed at children and has no minimum age; Art. 8 applies only to consent. If the
  owner learns that a child under 13 has an account, it is deleted (COPPA).
- **No DPIA:** none of the WP248 criteria clearly applies (no special categories, no monitoring or profiling, no
  large-scale tracking, no vulnerable groups targeted, no new technology).
